## Goal
A typed, validated, versioned content format (manifest + course files), one complete sample course to develop against,
a loader that turns files into safe typed objects (or a clear "not available" status), pure scoring helpers,
and the local Dexie database (progress, attempts, settings). Everything is covered by tests and lives in `src/core/`.

## Format decisions (made here, do not re-discuss)
- Content root (static files, later served by GitHub Pages): `public/content/`
  ```
  public/content/manifest.json
  public/content/courses/<courseId>/course.json      (card data: title, description?, cover?, order)
  public/content/courses/<courseId>/overview.json    (blocks, optional file)
  public/content/courses/<courseId>/content.json     (blocks, optional file)
  public/content/courses/<courseId>/test.json        (test, optional file)
  public/content/courses/<courseId>/images/<name>.webp|svg
  ```
  A missing or empty section file means "not available" (SPEC C3), never an error.
- `manifest.json`: `{ schemaVersion: 1, generatedAt: ISO string, courses: [ { id, title, version: number, files: { "<relative path>": "<sha256 hex>" } } ] }`.
  `version` grows by 1 on every publish of that course. The hashes let P11 download only what changed.
- IDs are stable and never reused: `<prefix>-<8 chars of [a-z0-9]>`: course `crs-`, block `blk-`, question `qst-`, test `tst-`.
  A rename or reorder never changes an ID. Generated by `newId(prefix)` using `crypto.getRandomValues`.
- Block (reader): `{ id, type: "title" | "subtitle" | "text" | "image", text?: string, src?: string, alt?: string }`.
  `title/subtitle/text` need non-empty `text`; `image` needs `src` (path relative to the COURSE folder, e.g. `images/a.svg`) and `alt` (may be empty string).
  Array order = display order. Every part optional means: an empty `blocks` array is valid.
- Test: `{ id, title?, image?, questionsPerGame: number >= 1, questions: [ { id, text, options: [4 strings], correctIndex: 0..3, explanation?: string } ] }`.
  `questionsPerGame` larger than the number of questions is allowed in the file; the game uses `min(questionsPerGame, questions.length)`.
  Exactly 4 options (SPEC D4). Options are NOT shuffled in the file; shuffling is a P07 runtime job.
- Stars (Q6): `starsForPercent(p)`: p >= 90 -> 5, >= 75 -> 4, >= 60 -> 3, >= 40 -> 2, else 1. Percent = round(correct / asked * 100).
- Validators are small hand-written functions (no schema library: keeps the bundle small and the error messages in our hands).
  They return `{ ok: true, value } | { ok: false, errors: string[] }` and never throw on bad input.
- Local DB: `dexie` (4.4.x line, Apache-2.0; verified current on 2026-11-18), tests use `fake-indexeddb` (MIT, dev only).
- The theme choice STAYS in `localStorage` key `np.theme` (changed from the P02 note): IndexedDB is asynchronous, and the theme must be
  applied before first paint to avoid a flash (P02 acceptance #4). Everything else goes to Dexie.
- Boundaries: `src/core/content` and `src/core/storage` must not import `src/modules` or `src/app`.

## Dexie schema v1 (`src/core/storage/db.ts`, database name `np-local`)
| Table | Primary key | Indexed fields | Holds |
|-------|-------------|----------------|-------|
| `profile` | `id` (always `"me"`) | - | optional name, email, phone |
| `readProgress` | `[courseId+blockId]` | `courseId` | which blocks were read, `readAt` (ms) |
| `attempts` | `++id` | `courseId`, `testId`, `at` | `courseId, testId, asked, correct, percent, stars, at` |
| `kv` | `key` | - | small settings (`value` any JSON) |
Encryption of this data is P04's job; the schema must make it possible to wrap reads/writes later (all access goes through `repo.ts`, never raw `db` in other files).
