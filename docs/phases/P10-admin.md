## Goal
A hidden Admin page (route `admin`, no tile, no menu entry) where the developer logs in with a GitHub token, creates and edits courses exactly as SPEC D2-D7 say, and keeps the result as validated drafts. Nothing in this phase changes what a normal user sees.

## Design (proposed here; T1 confirms with the owner and records DECISIONS Q24)
- Login (D1 allows (a) or (b)): a GitHub fine-grained personal access token limited to the ONE content repo (Contents: read and write). Check = `GET https://api.github.com/repos/<owner>/<repo>` and `permissions.push === true`; this is the "ID + password" of D1 and needs no secret file in the repo. The token is held in memory (and `sessionStorage` only if T1 says so); it is NEVER written to localStorage / IndexedDB / the user's encrypted store, never logged, never shown after entry. Repo owner/name come from one config file (`src/core/admin/config.ts`, T1 asks the owner for the values).
- Fingerprint at login (D1a): optional, reuse the existing fingerprint code only through `core/*`; decided in T1 (skip if it adds risk).
- Drafts: one draft per course (`CourseDraft` = course.json + overview blocks + content blocks + test + images as Blob / data URL), stored in IndexedDB through a small `core/admin/draftStore.ts` (unencrypted, it is public course material; the token is not in it). Images are shrunk in the browser (canvas -> webp) to a size limit decided in T1.
- Block editor (D3): optional Title and Subtitle boxes on top, then blocks; a "+" at the end adds a text or image block; blocks can be edited, removed, replaced, moved; IDs are created by `newId` and never change (CONTENT-FORMAT rules). Word paste: read the clipboard `text/html` with `DOMParser`, map headings -> title/subtitle, paragraphs -> text, images -> image blocks (or ask to upload); plain text paste splits on blank lines. No library.
- Test editor (D4, D7): paste or load a text file; a line starting with a number or "Q" is a question, 4 option lines follow, the BOLD one (`**text**`, or bold from pasted Word HTML) is the correct answer; the parser reports line numbers for a bad question. Form editing afterwards, `questionsPerGame` box (D7), optional title and image. The user never sees which option is bold (the file only gives `correctIndex`).
- Save / Add another course (D5) at the bottom; Edit (D6) opens a saved course from the drafts or loads it from `public/content` through `loader.ts`; add, remove, replace a part; delete a course asks for confirmation and marks it deleted in the draft state (the real delete is P11).
- Rendering never blocks; long Gujarati text wraps; keyboard works; `aria-live` for save / error messages; no raw errors shown.
